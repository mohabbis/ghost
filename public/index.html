The loop

Capture → Review → Approve → Execute → Verify → Recover

Agents may propose. Deterministic code executes only approved plans. Sensitivity is decided by a classifier — not a model hoping for the best. Agents never approve.

  1. 1

    Capture

    Demonstrate the workflow once. Compile into editable, typed steps. (Recording is the next build phase.)

  2. 2

    Review

    Inspect every step before it can run. No silent send, pay, or overwrite.

  3. 3

    Approve

    Risky steps halt. A human decides. The engine cannot skip the gate.

  4. 4

    Execute

    Replay via browser automation today; APIs/connectors next — still through the same pipeline.

  5. 5

    Verify & audit

    Assertions + screenshots per step. Hash-chained audit events per organization.

  6. 6

    Recover

    A broken step stops the run for a human — retry, skip, cancel — instead of killing a 40-invoice batch. Where a workflow defines a reversal, completed steps can be walked back through the same gate.

Proof, not pitch

What works in the repo today.

Phase 1 of the cloud product is runnable end-to-end against a bundled fixture: navigate → fill → halt on Submit → approve → resume → verify → succeed. If it isn’t in this list, don’t assume it ships.

  • Playwright execution engine Semantic selectors, per-step screenshots, verification assertions.
  • Deterministic approval gate classifyStep — not an LLM — decides what must wait for a human.
  • Durable execution Position is folded from an append-only journal, never a stored cursor — so a crash mid-run cannot re-fire an approved payment, and a redelivered job cannot repeat completed work. A time-based run lease keeps two workers off the same run in the ordinary case; it is not a fencing token, so a worker stalled past its lease can still overlap with the one that takes over.
  • Live run timeline Status, screenshots, approve/reject; resume restores browser state after the gate.
  • Incidents, retry and cancel A step that failed for a reason retrying could fix waits for a person instead of killing the batch. A rejected approval or a workflow that cannot resolve fails the run outright — retrying those changes nothing. Runs stop between steps; a step already in flight finishes, which is the honest behaviour for an action that must not happen twice.
  • Undo (compensation) Reverses completed steps in reverse order, through the same classifier, gate and journal — on a stricter bar than the forward path. A reversal is checked against its own assertion where the workflow defines one; otherwise the screenshot is evidence rather than proof. Effects with no defined reversal are reported, never quietly skipped.
  • Per-workflow concurrency cap An opt-in limit on how many runs of one workflow are in flight at once — off by default, and per workflow rather than per system, so it bounds a stampede rather than guaranteeing Ghost works a system alone. Held-back runs say why they are waiting.
  • Hash-chained audit log — and a verifier Per-org append-only events for run/step/gate/finish, with each run’s head anchored into the org chain. The chain can be re-checked in-product, not merely written — including deletion of a journal’s tail, which leaves every surviving link valid and so needs an expected head recorded outside it.
  • Agent HTTP + MCP tools List/preview/start runs from Cursor or Claude; approve stays human-only in Ghost UI.
  • Not built yet Browser recording, real connectors (email/CRM/ERP), billing, customer deployments.
  • Known limits of what is built Undo runs in a fresh browser session, so it only reaches systems that do not require a login. Journal tampering — edits, gaps, and deletion of the tail — is detected and quarantines the run, but every expected value lives in the same database as the thing it checks, and nothing is anchored anywhere outside it. So this catches corruption and a partial edit; it does not withstand someone with write access to the whole database. Tracked in the repo, not papered over.

Product sense

Who this is for — when it graduates.

The design target is operations-heavy SMBs (wholesale, bookkeeping, property admin, logistics) that re-key work between ugly systems and cannot accept unsupervised agents. That ICP guides the build even before the first paid pilot.

Cross-app grunt work

Reporting, reconciliation, document processing — repetitive and measurable.

Human on the sensitive step

Send, pay, delete, submit must stop. That constraint is the product, not a bug.

Proof afterward

Screenshots, verification, audit chain — something a manager can review.
